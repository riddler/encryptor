# ADR-0005: Rotation is three independent lifecycles, and only the shred is irreversible

Status: accepted (2026-08-27)

## Context

ADR-0003 built a three-level hierarchy and then handed every question about
its lifecycle to this record. ADR-0001 left `rekey/2` on the vault with a note
saying enc-53a should decide whether it belongs there. ADR-0002 observed that
"rotation is a list-membership property, and so is shredding" and assigned the
pruning policy here. And downstream, `encryptor_ecto`'s migrator record
(ece-ADR-0002) rests its entire no-downtime design on an assumption about what
this record decides. So this record is a joint: four open questions and one
downstream design all terminate in it.

The subject is smaller than "rotation" sounds, because the envelope design
already did the hard part. Nothing here invents a mechanism. The mechanisms are
`rekey/2` (ADR-0001 decision 4), `decryption_keys/2` returning a candidate list
(ADR-0002 decision 4), and an independently random tenant master key that can
actually be destroyed (ADR-0003 decision 1). What is missing is the sequencing:
which operations exist, in what order their steps must run, what is true between
the steps, what is recoverable when a step fails halfway, and which single step
is the one that cannot be undone.

Four forces bind the answers.

**The three levels rotate independently and at wildly different costs, and
conflating any two of them is how a rotation becomes a project.** ADR-0003's
levels are the root key (level 1), the tenant master key (level 2), and the
per-message data key (level 3). Rotating level 1 rewrites one row per tenant per
live version and touches no application data. Rotating level 2 requires every
ciphertext written under the outgoing version to be re-encrypted, which is a
walk over user tables. Level 3 rotates on its own, per message, and is bounded
by the materials cache, which is what ADR-0001 decision 6 made `max_age` a
required setting for. Three operations, three cost classes, three owners.

**The downstream record uses different names for the same levels, and the
mismatch is dangerous rather than cosmetic.** ece-ADR-0002 calls level 1 "the
key-encrypting key" and level 2 "a tenant's data key". Read against this
package's vocabulary, "the tenant's data key" is the tenant *master* key, and
the thing this package calls a data key (level 3, per message, generated by the
engine) has no row in the downstream table at all. An operator reading a runbook
written in one vocabulary against a package documented in the other can
plausibly run a level 2 rotation believing it is a level 1 rotation, which is
the difference between a five-minute pass over thousands of rows and a
multi-hour pass over millions. Decision 1 fixes the mapping in one table, in
both vocabularies, and this record uses this package's names everywhere else.

**A window between rotating and shredding is not a convenience, it is what
makes rotation runnable at all.** ece-ADR-0002's assumption A12 states it
plainly and calls itself load-bearing: if a rotated-away version stopped
decrypting the moment a new one became current, then re-encrypting a tenant's
rows would require stopping writes for the duration of the pass. The whole of
that record's compare-and-swap, probe-first, resumable design would be void.
This record has to say, unambiguously, whether the window exists, how long it
lasts, and what ends it. Decisions 2 and 3 do.

**A shred is the only operation in this package that destroys data, and it does
so at a distance.** Deleting a wrapping is a small write to one table that makes
an unbounded quantity of ciphertext in other tables permanently unreadable, and
nothing in the type system, the return values, or the database's own constraints
marks the difference between that delete and any other. Every procedure in this
record is reversible except the ones that end in a delete, and those are
reversible only up to the moment the last copy of the wrapping is gone. The
runbook's structure follows from that asymmetry: reversible steps are cheap and
may be retried freely, and the irreversible step is fenced with preconditions
that must be independently verified first.

This record owns the operator procedures, the live-set policy, the answers to
the downstream assumptions, and the blast radii. It does not own the row walk
over application data (ece-ADR-0002), the wrapped-key table (ece-ADR-0001 and
the store-backed provider), or the encryption context vocabulary (ADR-0004).

## Decision

**1. Four operations, three levels, one mapping table.** These are the only
things this package calls rotation or shredding, and every procedure in the
runbook below is one of them.

| This record | ece-ADR-0002 | Level | Rows rewritten | Function owner | Walk owner |
|---|---|---|---|---|---|
| Root rotation | R1 | 1 | one per tenant per live version, in the key store | `encryptor` | the key store's package |
| Tenant key rotation | R2 | 2 | every ciphertext for that tenant | joint, see decision 6 | `encryptor_ecto` |
| Format or context change | R3 | none in this package | every ciphertext in scope | `encryptor_ecto` | `encryptor_ecto` |
| Crypto-shred | R4 | 2 | one delete per shredded version | `encryptor` | the key store's package |

Data key rotation (level 3) is deliberately absent. It is not an operation an
operator performs; it happens on its own every `max_age`, every `max_messages`,
every `max_bytes`, and on every cache recycle, and the only lever on it is
ADR-0001 decision 6's configuration. A runbook step for it would be a runbook
step for restarting the vault.

R3 appears here only to be disclaimed. A change of format, algorithm, or
encryption context is a re-encrypt that this package's functions cannot express,
because `rekey/2` preserves the context byte for byte (ADR-0001 decision 4) and
the suite is vault configuration rather than a per-call option. It is entirely
downstream's, and decision 5 says why that is the correct place for it.

**2. The window exists, it is unbounded above, and only an explicit shred closes
it.** This is the answer to ece-ADR-0002's assumption A12, and it is yes.

The mechanism is already built. ADR-0002 decision 1 gives a provider two
separate resolution callbacks: `encryption_key/2` returns exactly one descriptor
and `decryption_keys/2` returns a list. Minting version *n+1* changes what
`encryption_key/2` answers. It does not change what `decryption_keys/2` answers
except by prepending to the list. The two are independent by construction, so
there is no ordering of operations, no race, and no deploy in which a version
becomes uncurrent and undecryptable at the same instant. A version stops
decrypting when, and only when, it stops appearing in `decryption_keys/2`, and
the only thing that removes it is an operator deleting the wrapping.

Three properties follow, and all three are load-bearing downstream:

- **There is no upper bound.** This package ships no timer, no expiry column, no
  TTL, no background sweeper, and no "retire versions older than N" helper. A
  version left live is live in five years. The window is as long as the
  operator's policy says, and the policy lives in the host's compliance
  documentation, not in this package's configuration. An automatic expiry would
  be a scheduled, unattended, silent data-destruction job, and this package
  declines to ship one.
- **There is a lower bound, and it is not zero.** A shred is safe only after the
  rewrite pass has finished, the verification pass is green, and every running
  vault has stopped serving the retired version out of its materials cache. The
  last term is easy to forget: ADR-0001 decision 6's cache holds resolved
  materials for up to `max_age`, so deleting a row does not stop a running node
  from decrypting under it. Decision 8's procedures make cache drainage an
  explicit step rather than an assumption.
- **Widening the window costs a list walk and nothing else.** ADR-0002's
  consequence about sixty-candidate walks and ADR-0003's about sixty small
  decrypts on a cold cache are the entire price of leaving a version live. It is
  bounded by the materials cache like every other resolution cost. Nothing about
  a long window is unsafe; the argument for closing it is that data whose key
  still exists is data that has not been shredded.

**3. Rotation adds a name and a shred removes one. There is no third mechanism,
and pruning is manual.** ADR-0002's consequence anticipated this and this record
ratifies it without addition.

Concretely, a live set is whatever the store answers `decryption_keys/2` with.
Rotation calls `Encryptor.Envelope.provision/3` with `version: n + 1` and the
host inserts the row; the new version is current because it is the highest, and
the old one is live because its row is still there. A shred deletes the row.
There is no state between live and gone, no soft-delete this package recognizes,
and no `retired_at` column it reads. ADR-0003 decision 9 already said this
package does not decide what "live" means and that the provider asks the store
and the store answers; decision 3 here is the operational half of that: whatever
the store's notion of liveness is, membership changes are the only rotation
mechanism, and every membership change is an operator action.

Consequently, pruning policy is count-based or age-based at the host's
discretion and this package expresses no preference beyond ADR-0003's
observation that many live versions cost one small decrypt each on a cold cache,
which argues weakly for a count bound. What this package does insist on is that
pruning is performed by the shred procedure in decision 8, with its
preconditions, and never as a side effect of anything else.

**4. Root rotation is staged with a candidate list on the root vault, and
`Encryptor.Provider.Static` gains one option to make that possible.** This
settles ADR-0003 open question 3.

The problem that question recorded is real: `rekey/2` re-encrypts under the
vault's currently resolved materials, but a rewrap pass over thousands of rows
is not atomic, so mid-pass some wrappings are under the outgoing root subkey and
some under the incoming one, and a root vault holding only the incoming subkey
cannot read the ones it has not reached yet. The fix is the same mechanism
tenant rotation already uses, applied one level up:

```elixir
Encryptor.Provider.Static
# today (ADR-0002's worked example):
  key: material, namespace: "encryptor-root", name: "r/v1"
# this record adds, mutually exclusive with :key:
  keys: [
    [key: new_material, namespace: "encryptor-root", name: "r/v2"],
    [key: old_material, namespace: "encryptor-root", name: "r/v1"]
  ]
```

With `keys:`, `encryption_key/2` returns the head of the list and
`decryption_keys/2` returns all of it, newest first, which is exactly the
contract ADR-0002 decision 1 already specifies. The vault then builds a `RawAes`
on the encrypt path and a `Multi` on the decrypt path with no change to the
vault at all. This is the "small `Static` extension" ADR-0003 open question 3
predicted, and it is small: one option, no new callback, no new descriptor, no
new error term. Passing both `:key` and `:keys` is
`{:error, {:invalid_config, :provider, :key_and_keys}}` at start.

Two constraints come with it. Because ADR-0001 decision 5 freezes configuration
into `:persistent_term` at start, changing the candidate list means restarting
the root vault, which is what that record's consequence about root rotation
warned. And because the root vault is configured `cache: false` (ADR-0003
decision 2), the restart costs nothing but the restart.

**5. The tenant-reference subkey is pinned to the root material that was current
when the deployment was first provisioned, and it is a separate configured
input from the wrapping subkey.** This is the part of root rotation ADR-0003
could not stage, and it needs stating carefully because it constrains a sibling
record's API.

ADR-0003 decision 6 expands two labels from the root key material, and its
consequence four observes that the reference subkey is effectively unrotatable
once the first message is written, because every stored `name` and every already
written message header carries a reference derived from it. Decision 6 separates
the *labels* so that the wrapping subkey can rotate without disturbing the
reference. But both labels are expanded from the same input, so rotating the
root key *material* rotates both, and consequence four's "effectively permanent"
property silently becomes "permanent unless someone rotates the root", which is
the thing the runbook is for.

Therefore: after the first root rotation, a deployment supplies two independent
root inputs.

| Input | Expands | Lifecycle |
|---|---|---|
| the reference root | `"encryptor/v1/tenant-ref"` | pinned at generation 1, never rotated |
| the wrapping root | `"encryptor/v1/root-wrap"` | rotated by procedure P1 |

Before the first rotation they hold the same bytes, and step 0 of procedure P1
is to copy the current root into the reference-root secret so that the two can
then diverge. No API change is required for the derivation itself:
`Encryptor.Envelope.root_subkey/2` already takes the root key material as an
explicit argument rather than reading it from a vault (ADR-0003's typespecs), so
a host simply passes different binaries for the two labels.

One API in ADR-0003 does not survive the split, and this record flags it rather
than editing a sibling. `Encryptor.Envelope.tenant_ref(root_vault, selector)`
takes a root vault, but a root vault holds only the wrapping subkey as its
`Static` provider material, and after P1 that is no longer the input the
reference derives from. The signature therefore has to become one that takes the
reference subkey (or a configuration that holds it) rather than one that infers
it from the root vault. Recording it as open question 1 rather than rewriting
ADR-0003's typespec is deliberate: it is a real correction to an unaccepted
sibling record and the operator should make it at acceptance, with both records
in front of them.

**6. Tenant key rotation is a joint operation, and the seam runs between the key
lifecycle and the row walk.** ece-ADR-0002 assigns R2 to itself. That is right
about the expensive half and incomplete about the whole, so the split is stated
here in full:

1. **Mint** (`encryptor`): `provision/3` with the next version, the host inserts
   the row. Version *n+1* becomes current. Nothing else changes.
2. **Rewrite** (`encryptor_ecto`): the migrator's pass over the tenant's rows,
   filtered to that tenant, with `from` and `to` naming the same type module.
   Every row it rewrites is re-encrypted under whatever `encryption_key/2` now
   answers, which is *n+1*, without the migrator naming a version. This is
   downstream's assumption A10 and it holds.
3. **Verify** (`encryptor_ecto`): the verification pass over the same scope,
   green.
4. **Retire** (`encryptor`): shred version *n*. Irreversible. Fenced by step 3.

Steps 1 and 4 are key-store operations and belong here. Steps 2 and 3 are row
operations and belong downstream. The window of decision 2 is the span from the
end of step 1 to the start of step 4, and it is open for the entire duration of
the pass, which is the property that makes the pass safe against live traffic.

Nothing in this package walks application data. There is no `encryptor` function
that takes a table, a repo, a query, or a batch size, and there will not be one,
because the seam ece-ADR-0002 decision 9 drew is the right one read in both
directions: an operation needed by a host that stores ciphertext somewhere other
than Ecto belongs here, and an operation that needs a `Repo` does not.

**7. `rekey/2` stays on the vault, and its caller is the envelope rather than
the migrator.** This settles ADR-0001 open question 5, and it settles it against
that question's own hypothesis.

The question supposed that the only real caller might be `encryptor_ecto`'s
re-wrap task, in which case the vault surface would be smaller without it. Two
findings say otherwise. ADR-0003 decision 2 already builds
`Encryptor.Envelope.rewrap/2` on `rekey/2` semantics, so root rotation is a
first-class in-package caller and removing `rekey/2` would mean reimplementing
it inside the envelope with no gain. And the downstream migrator turns out not
to be a caller at all: its probe-first classification loads and dumps through
the Ecto type on every row (ece-ADR-0002 decisions 5 and 8), and it must handle
R3, where the format or the context changes and a context-preserving rekey is
by definition the wrong operation. A tool that is uniform across R2 and R3
cannot be built on `rekey/2`.

So `rekey/2` is kept, and its documentation says what it is for and what it is
not for: it re-encrypts one message under current materials with the context
preserved byte for byte, its canonical caller is `Envelope.rewrap/2`, it is
available to a host that stores ciphertext outside Ecto and wants R2's rewrite
without the migrator, and it is not the migrator's tool.

**8. The runbook. Four procedures, each with preconditions, steps, and an
independent verification.** These are operator procedures. Every step is a
function this package ships or an action on a store this package does not own,
and the split is called out per step.

---

### P1. Root rotation (R1, level 1)

Rotates the wrapping subkey. Touches no application data.

**Preconditions**

- The reference root is pinned in its own secret (decision 5). On a first
  rotation this is step 0 and it is a copy, not a new value.
- The key store can enumerate every wrapping for every live version.
- The store's update of a wrapping is a single-row write that can be retried.

**Steps**

0. If this is the first rotation of this deployment, copy the current root
   material into the reference-root secret. Deploy and restart. Nothing has
   changed cryptographically; this step exists so that step 2 does not move the
   reference.
1. Generate new root material and place it in the wrapping-root secret,
   alongside the outgoing value.
2. Configure the root vault's `Static` provider with `keys: [new, old]`
   (decision 4), newest first, with distinct `name`s. Restart the root vault.
   Reads now succeed under either subkey; writes use the new one.
3. Walk every live wrapping and call `Encryptor.Envelope.rewrap/2` on it,
   persisting the result. Order does not matter and the pass is resumable: a
   row already under the new subkey rewraps to itself, so re-running the pass
   is idempotent up to the ciphertext bytes changing.
4. Verify (below). Then remove the outgoing entry from `keys:` and restart the
   root vault.
5. Destroy the outgoing root material from the secret store, once backups taken
   before step 4 are out of retention or are known to be re-encrypted.

**Verification**

- Every wrapping's header names the new root key. The wrapping key's `name`
  travels in the clear in the EDK's provider info (ADR-0002 decision 4), so
  this is a census over stored bytes rather than a decrypt pass, subject to
  open question 3.
- A sample of tenants resolves: `decryption_keys/2` returns descriptors and a
  test decrypt of one known ciphertext per sampled tenant succeeds.
- After step 4, the outgoing root material no longer decrypts anything: a
  deliberate attempt with the old-only configuration in a scratch environment
  should fail.

**Failure and rollback**

Reversible at every step until step 5. A pass interrupted at step 3 leaves a
mixed population that both configurations can read, which is precisely why
step 2 precedes it. To roll back, reverse the order of `keys:` and re-run
step 3; the outgoing subkey becomes current again. The one irreversible action
is step 5, and it is separated from the rest by an explicit verification.

---

### P2. Tenant key rotation (R2, level 2)

Rotates one tenant's master key. Every ciphertext for that tenant is rewritten.

**Preconditions**

- The tenant has at least one live version and its current version resolves.
- The downstream migrator has a plan covering every table and column holding
  that tenant's ciphertext. A column missed here is a column whose rows become
  unreadable at P4, which is the failure mode this whole record exists to
  prevent.
- Enough time budget to complete the rewrite before the retire; the two are not
  required to be in the same maintenance session, and they should not be.

**Steps**

1. `Encryptor.Envelope.provision/3` with `version: n + 1`; the host inserts the
   row. Version *n+1* is now current for new writes; *n* remains live.
2. Run the migrator over the tenant's scope. This is downstream's tool and
   downstream's runbook; nothing in this package participates.
3. Run the verification pass over the same scope, whole scope rather than a
   sample.
4. Only when step 3 is green, run P4 for version *n*.

**Verification**

- The migrator's verifier exits zero over the full scope.
- No row remains whose header names version *n*, per the same census as P1's
  verification and the same caveat.
- The tenant's `decryption_keys/2` still contains both versions at this point.
  If it does not, something removed a version outside this procedure and P4 must
  not be run until that is understood.

**Failure and rollback**

Fully reversible until step 4. An interrupted rewrite leaves rows under both
versions, all readable, and the pass resumes. Rolling back the rotation itself
means making *n* current again, which is a provisioning question the host's
store answers, and the already-rewritten rows stay readable either way because
both versions are live. There is no state in this procedure, before step 4, from
which data can be lost.

---

### P3. Tenant shred (R4, offboarding)

Destroys every version of one tenant's master key. Irreversible.

**Preconditions**

- A recorded, human decision that this tenant's data is to be destroyed, with a
  reference to it in the change record. This package's position is that a shred
  is never automated and never a cascade from a `DELETE` on a tenants table.
- Every legitimate consumer of that tenant's data has been identified. After
  this procedure, no amount of key material recovers it.
- The backup implications below have been read and accepted.

**Steps**

1. Confirm the tenant reference resolves and enumerate the wrappings that are
   about to be destroyed. Record the count and the version numbers in the change
   record.
2. Delete every wrapping for the tenant from the key store.
3. Drain the caches: either wait `max_age` on every vault that serves the
   tenant, or restart those vaults. Until this step completes, a running node
   can still decrypt the tenant's data from cached materials (ADR-0001
   decision 6).
4. Optionally delete the tenant's ciphertext rows. This is hygiene, not the
   shred; after step 3 those rows are unreadable bytes.

**Verification**

- `encrypt/2` and `decrypt/2` for that tenant return
  `{:error, %Encryptor.Error{reason: {:unknown_key, selector}}}`, not
  `:decrypt_failed`. This is the distinguishability property decision 9 fixes,
  and it is the acceptance test for the shred.
- The key store returns no rows for the tenant reference.
- A ciphertext known to belong to the tenant does not decrypt from any node.

**Failure and rollback**

None after step 2. A partially completed step 2 leaves some versions live and
some destroyed, which is the per-version case in decision 9 and is the worst
state this record has: some rows readable, some permanently not, and the two
indistinguishable to the application. If step 2 fails partway, complete it
rather than reverting it, and record what was destroyed.

---

### P4. Version retire (R4, one version)

Closes the window opened by P2. Irreversible.

**Preconditions**

- P2 steps 2 and 3 completed and green, over the whole scope, not a sample.
  This is the fence. There is no legitimate reason to retire a version whose
  rows have not been verifiably rewritten.
- The verification is recent enough that no traffic since could have written
  under the retired version. It cannot have: `encryption_key/2` has answered
  *n+1* since P2 step 1. This precondition is about the operator's confidence
  in the scope, not about the mechanism.
- Cache drainage is understood to be part of this procedure, not a follow-up.

**Steps**

1. Delete the wrapping for version *n*.
2. Drain the caches, as P3 step 3.

**Verification**

- `decryption_keys/2` for the tenant no longer contains version *n*.
- The application's error rate for that tenant is unchanged. A rise in
  `:decrypt_failed` means rows were missed, and they are now unrecoverable.

**Failure and rollback**

None. This is the irreversible step of P2, deliberately given its own procedure
so that it is a separate decision with its own preconditions rather than the
last line of a longer one.

---

**9. A whole-tenant shred is distinguishable from corruption; a single retired
version is not.** This is the answer to ece-ADR-0002's assumption A13, and it is
a partial yes.

When every version of a tenant is gone (P3), the provider's store finds no live
row, `decryption_keys/2` returns `{:error, {:unknown_key, selector}}` per
ADR-0003 decision 8's account of an unknown selector, and the failure surfaces at
resolution time before any ciphertext is examined. ADR-0002 decision 6 already
carved provider resolution out of ADR-0001's collapse-everything rule precisely
because it depends only on the caller's selector and is therefore not a
decryption oracle. So a shredded tenant is loudly and specifically distinct from
a corrupt message, which is what A13 needs.

When one version among several is retired (P4), it is not. A message written
under the retired version fails as `:decrypt_failed`, identical to a corrupted
message, a wrong-key message, and a context mismatch, because ADR-0001
decision 10 collapses the whole decrypt-side failure space to one reason and
this record does not reopen that. ADR-0002's consequence about a provider bug
returning a short list being indistinguishable from a deliberate shred is the
same observation, and it is not fixable at this layer without building the
oracle ADR-0001 refused.

The operational answer is the fence, not a new error term. P4's precondition is
a green whole-scope verification, so a `:decrypt_failed` after a retire means a
row the plan did not cover, which is a bug in the plan rather than an ambiguity
in the error. Downstream's decision 11 already expresses shredded tenants as a
tenant filter rather than as tolerated errors, which is the correct shape and
works for P3; for P4 there is nothing to filter, because after a correct P4 no
row references the retired version.

**10. What this package ships, and what it only documents.** The bead asks for
this line to be explicit, and decision 6's seam makes it easy to draw.

Shipped, as functions:

- `Encryptor.Envelope.provision/3`, which mints a version (P2 step 1).
- `Encryptor.Envelope.rewrap/2`, which rewraps one wrapping (P1 step 3).
- `Encryptor.Vault.rekey/2`, which `rewrap/2` is built on (decision 7).
- `Encryptor.Provider.Static`'s `keys:` option (decision 4).

Documented, as procedures: all four of decision 8, including every step that
touches a store this package does not own.

Not shipped, and deliberately:

- No `mix` task. Every procedure needs a store this package has no access to,
  so a task here could only be a task that takes a callback, which is a runbook
  with a worse interface.
- No scheduler, no expiry, no automatic pruning (decision 2).
- No walk over anything. No function here takes a repo, a query, a batch size,
  or a table.
- No shred function. Deleting a wrapping is a `DELETE` against the host's store,
  and wrapping it in an `Encryptor.shred/2` would imply this package knows what
  the store's copies are, which decision 11's backup discussion says it does
  not.

## Consequences

**The window is now a documented operational parameter with no default.** A host
must decide how long a retired version stays live, and this package will not
decide for it, will not warn about it, and will not report on it. That is
consistent with ADR-0001 declining a default for `max_age` on the same grounds,
and it has the same cost: a host that never runs P4 accumulates versions
forever, and a host that runs it too eagerly loses data. The mitigating fact is
that P4's precondition is machine-checkable downstream and the runbook says so.

**A shred is only as good as the copies, and this record cannot improve on
that.** ADR-0003 decision 10 already stated it and P3 restates it as a
precondition, but it deserves a consequence of its own because it is the single
largest gap between what a shred claims and what it achieves. Deleting a
wrapping destroys the key in the primary store. It does nothing about database
backups taken while the wrapping existed, read replicas that have not yet
received the delete, a logical dump on someone's laptop, a wrapping exported
into a disaster-recovery vault, or a snapshot of a running node's memory. A host
whose compliance story is "we crypto-shred on offboarding" has committed to a
backup retention and replica story that this package cannot see and does not
verify. Stating the limit is the most this record can honestly do.

*(Added at acceptance, 2026-08-27.)* A shred destroys plaintext, not
attribution. Every message header carries the tenant's permanent pseudonym -
the `tenant_ref`, in the EDK key name and (per ADR-0004's amended
decision 4) in the encryption context - and deleting the wrapping does not
touch it. Outsiders cannot resolve the pseudonym; the holder of the
reference subkey can, by guess-and-confirm, forever, in every retained
backup. P3 step 4's row deletion is therefore compliance-mandatory wherever
tenant attribution itself is personal data, not hygiene, and the shred
claim must never be stated as full erasure.

**Root rotation now requires two secrets where there was one.** Decision 5's
split is a real operational cost: a deployment provisioned before its first
rotation has one root secret and must grow a second, and getting step 0 wrong -
generating a fresh value for the reference root rather than copying the current
one - changes every tenant reference and orphans every stored name and every
written header. That is the most destructive single mistake available in this
record, and it is a copy-paste step that looks like a no-op. It is fenced in P1
by being step 0 with its own explanation, and it is the reason open question 1
wants ADR-0003's `tenant_ref/2` signature corrected at acceptance rather than
left to be discovered.

**The downstream migrator's design is confirmed, with one assumption
corrected.** A12 holds as stated. A10 and A11 hold. A13 holds for whole-tenant
shreds and not for retired versions, and downstream's own decision 11 already
uses the shape that works. A14 - "re-wrap of wrapped tenant keys is offered by
`encryptor` and needs nothing from the Ecto layer" - does not hold as written,
and its correction is the next consequence.

**R1 needs nothing from the migrator, but it does need the key store, and the
key store is an Ecto table.** This is downstream's open question Q3 and the
answer is that the seam is drawn in the right place but described one notch too
broadly. ADR-0003 decision 9 puts the wrapped-key storage in `encryptor_ecto`,
and ADR-0002 decision 5 puts the store-backed provider there too. So P1 step 3's
walk over live wrappings and P3 step 2's delete are operations on an Ecto table
in that package. What they are not is migrator operations: they take no plan, no
checkpoint, no compare-and-swap, no batch, and they never touch a ciphertext
column of a host table. The workable shape is a narrow key-store API on the
store-backed provider - enumerate live wrappings, update one wrapping, delete
one wrapping - that is not part of the migrator's plan format or task list, so
ece-ADR-0002 decision 9's refusal ("this package's task list contains no verb
that operates on a key") survives intact for the migrator while R1 and R4 get
the iteration they need. A14 should read "needs nothing from the migrator".
Recorded as open question 2, because it is a correction to a sibling record in
another repository and this record does not edit one.

**Cache drainage is now a runbook step and an operator will forget it.** P3
step 3 and P4 step 2 are the least intuitive steps in this record: an operator
who has deleted a row reasonably believes the key is gone, and for up to
`max_age` on every running node it is not. There is no way for this package to
enforce the drain, because ADR-0001 decision 6 records that `LocalCache` cannot
be enumerated, measured, or selectively invalidated from outside. The only
levers are waiting or restarting, and both are documented as such. If the
upstream engine ever grows the bounded, inspectable cache ADR-0001 open
question 3 wants, a targeted invalidation becomes possible and these two steps
get sharper.

**Nothing here is testable end to end inside this package.** Every procedure
crosses into a store this package does not have. What is testable here is the
per-row half: that `keys:` produces the right keyring on each path, that
`rewrap/2` round-trips a wrapping under a rotated root, that a wrapping rewrapped
under the new root still unwraps to the identical descriptor, and that a
descriptor whose version has been removed from a candidate list produces
`:decrypt_failed` while a tenant with no versions produces `{:unknown_key, _}`.
The procedures themselves are verified in `encryptor_ecto`'s integration tests
or not at all, which is an argument for that package's restart-and-rotate demo
covering P1 and P2 rather than only the migrator.

## The contract as typespecs

This record adds no module and no error term. It adds one provider option and
fixes the semantics of functions ADR-0003 already specified.

```elixir
defmodule Encryptor.Provider.Static do
  @typedoc """
  One key entry. `:name` is the version identity that travels in the clear
  (ADR-0002 decision 4) and must be distinct per entry.
  """
  @type entry :: [
          key: binary(),
          namespace: String.t(),
          name: String.t()
        ]

  @typedoc "Exactly one of :key or :keys. `:keys` is newest first."
  @type opts ::
          [key: binary(), namespace: String.t(), name: String.t()]
          | [keys: [entry(), ...]]
end
```

The added start-time reason, in ADR-0001 decision 10's existing
`{:invalid_config, key, detail}` shape rather than as a new term:

```elixir
{:invalid_config, :provider, :key_and_keys}
```

The rotation-relevant halves of ADR-0003's envelope surface, restated with the
semantics this record fixes:

```elixir
@doc """
Mint version `n + 1` for a tenant. P2 step 1. Never removes a version and never
changes what `decryption_keys/2` already returns for existing versions.
"""
@spec provision(root_vault(), selector(), opts()) ::
        {:ok, Encryptor.Envelope.WrappedKey.t()} | {:error, Encryptor.Error.t()}

@doc """
Re-wrap one wrapping under the root vault's current materials. P1 step 3.
Idempotent in effect: a wrapping already under the current root rewraps to an
equivalent wrapping (different bytes, identical descriptor on unwrap).
"""
@spec rewrap(root_vault(), Encryptor.Envelope.WrappedKey.t()) ::
        {:ok, Encryptor.Envelope.WrappedKey.t()} | {:error, Encryptor.Error.t()}
```

There is deliberately no `shred/2`, no `retire/2`, and no `rotate/2`. Decision
10 says why.

## The blast radius table

Per the bead's acceptance criterion. "Reversible" means reversible by an
operator holding everything they held before the step, without recourse to
backups.

| Procedure | Step | Destroys | Reversible | If performed wrongly |
|---|---|---|---|---|
| P1 | 0, copy reference root | nothing | yes | If a fresh value is generated instead of a copy: every tenant reference changes, every stored `name` and every written header orphans. All tenants, all data, recoverable only by restoring the original root material. |
| P1 | 2, restart with `keys:` | nothing | yes | Wrong order: writes go under the outgoing subkey. Harmless while both are live. |
| P1 | 3, rewrap pass | nothing | yes | Partial pass leaves a mixed population, all readable. Resume or reverse. |
| P1 | 4, drop outgoing entry | nothing yet | yes, by re-adding it | Dropped before the pass finishes: unrewrapped wrappings stop unwrapping, so their tenants stop resolving. Recoverable by re-adding the entry. |
| P1 | 5, destroy old material | the ability to read pre-rotation backups | no | Backups taken before step 3 become unreadable. Bounded by backup retention. |
| P2 | 1, mint | nothing | yes | Minting twice concurrently can produce two version *n+1* rows; ADR-0003 open question 1 owns that race. |
| P2 | 2, rewrite | nothing | yes | Downstream's compare-and-swap; a clobber is the failure it is designed against. |
| P3 | 2, delete all wrappings | one tenant's entire dataset, everywhere | **no** | Wrong tenant: that tenant's data is permanently unreadable. This is the largest destructive action in the package and the reason P3's first precondition is a recorded human decision. |
| P3 | 3, drain caches | nothing | n/a | Skipped: the shred is incomplete for up to `max_age`, and the tenant's data remains readable on running nodes. |
| P4 | 1, delete one wrapping | every row still written under that version | **no** | Run before verification: exactly the rows the pass missed become permanently unreadable, and they surface as `:decrypt_failed` indistinguishable from corruption. |
| any | shredding a tenant master key | that tenant's derived subkeys too | **no** | ADR-0003 decision 7's subkeys are recomputed from the master key and never stored, so a blind index, a search key, or any future purpose-labelled key dies with it. This is intended and is a property, but it means a shred is wider than "columns encrypted by this package". |

## Worked example: rotating a root without moving a reference

The state before, a deployment on its original root, and the change to P1
step 0's shape.

```elixir
defmodule MyApp.RootVault do
  use Encryptor.Vault, otp_app: :my_app

  @impl true
  def init(config) do
    wrap_root = Base.decode64!(System.fetch_env!("MY_APP_ROOT_KEY"))

    {:ok,
     Keyword.put(config, :provider,
       {Encryptor.Provider.Static,
        key: Encryptor.Envelope.root_subkey(wrap_root, "root-wrap"),
        namespace: "encryptor-root",
        name: "r/v1"})}
  end
end
```

After P1 step 0 and step 2, mid-rotation, both subkeys live:

```elixir
defmodule MyApp.RootVault do
  use Encryptor.Vault, otp_app: :my_app

  @impl true
  def init(config) do
    new_root = Base.decode64!(System.fetch_env!("MY_APP_ROOT_KEY"))
    old_root = Base.decode64!(System.fetch_env!("MY_APP_ROOT_KEY_PREVIOUS"))

    {:ok,
     Keyword.put(config, :provider,
       {Encryptor.Provider.Static,
        keys: [
          [key: Encryptor.Envelope.root_subkey(new_root, "root-wrap"),
           namespace: "encryptor-root", name: "r/v2"],
          [key: Encryptor.Envelope.root_subkey(old_root, "root-wrap"),
           namespace: "encryptor-root", name: "r/v1"]
        ]})}
  end
end
```

`MY_APP_REF_ROOT_KEY` holds the generation-1 material and is read wherever a
tenant reference is derived, which after open question 1 is settled is not from
this vault.

The pass, which is ADR-0003's worked example unchanged, now safe mid-flight:

```elixir
for row <- MyApp.TenantKeys.all_live() do
  {:ok, rewrapped} = Encryptor.Envelope.rewrap(MyApp.RootVault, row)
  MyApp.TenantKeys.update_wrapping(row, rewrapped)
end
```

What this is chosen to demonstrate:

- **The pass is unchanged.** Decision 4's whole job is to make the mid-pass
  state readable so that ADR-0003's four-line loop stays four lines.
- **Two secrets, two labels, two lifecycles**, visible in one `init/1` rather
  than explained in prose.
- **`name` is what makes the census work.** `"r/v1"` and `"r/v2"` are in the
  clear in every wrapping's header, which is what P1's verification counts.
- **Step 4 is deleting six lines.** Removing the old entry and restarting is the
  entire close-out, which is what makes it easy to do too early.

## Worked example: a tenant rotation and its window

```elixir
# P2 step 1. Upstream. The window opens here.
{:ok, wrapped} =
  Encryptor.Envelope.provision(MyApp.RootVault, tenant.id,
    namespace: "acme-tenant",
    version: 2
  )

{:ok, _row} = MyApp.TenantKeys.insert(wrapped)

# Both versions resolve. New writes take v2; old rows still open under v1.
{:ok, [%Encryptor.Key.Aes{name: v2}, %Encryptor.Key.Aes{name: v1}]} =
  MyApp.TenantKeyProvider.decryption_keys(state, tenant.id)
# v2 is "t/<tenant_ref>/v2", v1 is "t/<tenant_ref>/v1", newest first.
```

```elixir
# P2 steps 2 and 3. Downstream. Days may pass here; the window stays open.
Encryptor.Ecto.Migrator.run(MyApp.Encryption.Rotate, mode: :write, only_tenants: [tenant.id])
Encryptor.Ecto.Migrator.verify(MyApp.Encryption.Rotate, sample: :all)
```

```elixir
# P4. Upstream. The window closes here, irreversibly.
MyApp.TenantKeys.delete_version(tenant.id, 1)
# then drain: wait max_age, or restart the tenant vault.
```

```elixir
# The two failure shapes, after the two different destructive operations.

# After P4 with a row the plan missed - indistinguishable from corruption:
MyApp.TenantVault.decrypt(missed_row_ct, key: tenant.id, encryption_context: %{...})
#=> {:error, %Encryptor.Error{reason: :decrypt_failed, operation: :decrypt}}

# After P3, the whole tenant - specific, and not an oracle:
MyApp.TenantVault.decrypt(any_ct, key: shredded.id, encryption_context: %{...})
#=> {:error, %Encryptor.Error{reason: {:unknown_key, "..."}, operation: :decrypt}}
```

What this is chosen to demonstrate:

- **The window is three code blocks wide and there is nothing in the middle
  one from this package.** That separation is the whole of decision 6.
- **Nothing forces the third block to ever run**, which is decision 2's "no
  upper bound" made concrete.
- **The two error shapes are the acceptance tests** for P3 and, by their
  absence, for P4. Decision 9's partial answer to A13 is visible rather than
  argued.

## Open questions

Recorded rather than guessed. Each names who should settle it. The first two are
acceptance-blocking in the sense that they are corrections to sibling records
that this record deliberately did not make itself.

1. **`Encryptor.Envelope.tenant_ref/2` cannot take a root vault once decision 5
   splits the roots.** A root vault holds the wrapping subkey; the reference
   derives from the pinned reference root. The signature needs to take the
   reference subkey, or a configuration holding it, instead. Related: whether
   the reference root belongs in the tenant vault's configuration, in the
   envelope's own configuration, or as a bare argument. Owner: ADR-0003, at
   acceptance, with this record in front of the reviewer.

   *Resolved at acceptance (2026-08-27): ADR-0003's `tenant_ref/2` is amended
   to take the reference subkey. The subkey lives in tenant-vault
   configuration (ADR-0004's amended decision 4, which also puts the derived
   reference into the application-data context and adds a start-time
   known-answer check on the subkey); the store-backed provider derives
   references from selectors with the same subkey.*

2. **ece-ADR-0002's assumption A14 should read "needs nothing from the
   migrator".** R1 and R4 need to enumerate, update, and delete rows in the
   wrapped-key table, which ADR-0003 decision 9 places in `encryptor_ecto`. The
   proposed shape is a narrow key-store API on the store-backed provider,
   outside the migrator's plan and task surface, which preserves that record's
   decision 9 exactly. This is that record's open question Q3, answered from
   this side. Owner: ece-56a, at acceptance; the API itself is enc-2u6's
   store-backed provider work.

   *Resolved at acceptance (2026-08-27): ece-ADR-0002's A14 is reworded to
   "needs nothing from the migrator" at its own acceptance, with the narrow
   key-store API recorded as this consequence proposes.*

3. **Whether a message's key `name` can be read without a decrypt, and at a
   stable offset.** P1's and P2's verifications are censuses over the wrapping
   key name and the tenant key name in the clear in the message header. ADR-0001
   open question 1 already floats a read-only `inspect/1`, and ece-ADR-0002's
   assumptions A8 and A9 and its open question Q2 want the same thing for the
   SQL census. Three records now want one function. Until it exists, every
   verification in decision 8 that says "census" is a decrypt pass instead, which
   is affordable for the wrapped-key table (thousands of rows) and not for the
   application tables (millions). Owner: ADR-0001 or a record of its own; this
   record is the third caller and should be cited when it is decided.

4. **Whether P4 should be blocked on something machine-checkable rather than on
   an operator's reading of a verification report.** Everything that makes P4
   safe lives downstream: the plan's coverage, the verifier's exit code, the
   scope. This package's shred is a `DELETE` it does not perform and cannot
   gate. A host could wire the gate itself (refuse the delete unless a
   verification record exists and is recent), and whether this package should
   document that pattern or ship a shape for it is worth deciding once a real
   host has run P2 twice. Owner: operator, after the first real rotation.

5. **What the reference-root secret is called and how a fresh deployment is
   stopped from getting P1 step 0 wrong.** Consequence three identifies step 0
   as the most destructive-looking no-op in the record. A deployment that
   provisions both secrets at install time, equal, never has to perform step 0
   and cannot get it wrong. That argues for the installation documentation
   requiring two secrets from day one rather than introducing the second at
   first rotation. It is a documentation decision with a real safety payoff and
   it wants the getting-started guide to exist first. Owner: this repository,
   before the first release.

6. **Whether a retired version should be recoverable for a grace period.** P4 is
   irreversible by design, but a host could keep the outgoing wrapping in a
   separate, more restricted store for a fixed period, which converts P4 from a
   destruction into a move and gives an operator a way back from a missed table.
   It also means the shred claim in P3 becomes conditional on that store, which
   is exactly the "only as good as the copies" problem, deliberately reintroduced.
   The two are in genuine tension and neither is obviously right. Owner:
   operator, and it should be decided as a policy rather than as a feature.

7. **Whether rotation cadence guidance belongs in this package at all.**
   ADR-0003 decision 10 observes that tenant compromise is bounded by version
   rather than by time, which makes cadence a security parameter with an
   argument attached rather than hygiene. This record gives no numbers and no
   default, consistent with declining to ship a scheduler, but a package that
   documents four procedures and no guidance on when to run them is arguably
   half a control. Owner: whoever writes the security section of the
   documentation, with ADR-0001 open question 2's unmeasured cache bounds.
